\section{Tournament Branch Predictor}

\subsection{Design}

\subsubsection{Prediction}

The tournament branch predictor consists of three components:
\begin{enumerate}
    \item GAg predictor. The global branch history is mapped to a saturating counter via a table-lookup, and used to make a prediction.
    \item PAg predictor. The program counter is mapped to a local branch history via a table-lookup. Then, the local branch history is mapped to a saturating 
    counter via another table-lookup, and used to make a prediction. The second table is shared between all local branch histories.
    \item Bimodal choice predictor. The program counter is mapped to a saturating counter via a table-lookup, and used to predict whether the GAg or PAg 
    prediction should be used.
\end{enumerate}

\noindent
The size of the four tables, the number of bits in the global and local branch histories, and the number of bits in the saturating counters are left as 
compile-time parameters. The saturating counters are always initialized to weakly-taken. This implies that GAg is the default predictor during warmup.

\subsubsection{Update}

Each of the three components are updated independently:
\begin{enumerate}
    \item GAg predictor. The global branch history is extended with the actual branch result. The saturating counter is increased if the branch was taken, and 
    decreased otherwise.
    \item PAg predictor. The local branch history is extended with the actual branch result. The saturating counter is increased if the branch was taken, and
    decreased otherwise.
    \item Bimodal choice predictor. The update only occurs if the GAg and PAg predictions disagreed. In this case, the saturating counter is increased if GAg 
    was correct and decreased if PAg was correct.
\end{enumerate}

\section{Hashed Perceptron Branch Predictor}

\subsection{Design}

The hashed perceptron branch predictor implementation follows the provided \texttt{ChampSim}\footnote{https://github.com/ChampSim/ChampSim} implementation 
without dynamic update thresholds. For simulation purposes, the XXH32 hash function was used for all reductions. In real hardware, it should be replaced with an
efficient reduction scheme.

\subsubsection{Prediction}

During prediction, a series of perceptron weight tables are indexed with a global history combined with the current program counter, where the length of each 
global history is geometrically increasing. The corresponding perceptron weights are summed, and compared against a static decision threshold. 

\subsubsection{Update}

If the prediction was incorrect, each corresponding perceptron weight is increased, or decreased by one, to drive the perceptron output closer to, or across the
decision threshold.

\section{Custom Branch Predictor}

\subsection{Failed Designs}

I was unable to significantly outperform the \texttt{ChampSim} hashed perceptron implementation. Here are a few highlights from what I tried:
\begin{enumerate}
    \item I implemented TAGE based on my lecture notes ($\approx 10$ arithmetic mean MPKI), with valid bits for table entries ($\approx 5$ arithmetic mean 
    MKPI), with a meta predictor and Gshare fallback (regression), with a loop predictor (regression), and several other tweaks (regression).
    \item  I implemented TAGE as described in~\cite{seznec2006} with valid bits for table entries ($\approx 3.5$ arithmetic mean MPKI), and several other tweaks
    (regression).
    \item I implemented a tournament between hashed perceptron and Gshare (regression).
\end{enumerate} 

\subsection{Final Design}

My final branch predictor is the hashed perceptron predictor with O-GEHL dynamic update thresholds (as in \texttt{ChampSim}) and path history for tables with 
short global history lengths~\cite{seznec2005}. 

\subsubsection{Prediction}

Prediction is the same as hashed perceptron, except for history lengths below the path history maximum history bits, the path history is folded into the table
index. The path history is implemented as a sequence of 4-bit hashes of previous program counters.

\subsubsection{Update}

Update is the same as hashed perceptron, except the perceptron weights are also updated on a weak prediction. Weak predictions are defined by the O-GEHL dynamic
update threshold algorithm. The PC is also folded into a 4-bit hash, and added to the path history.

\section{Lessons Learned}

In the future, I need to:
\begin{enumerate}
    \item Design reusable abstractions. I had a hard time writing correct predictors and iterating quickly without good data structural abstractions (e.g. 
    saturating counters).
    \item Implement a tracing framework. I wasn't able to design effective tweaks  because I did not trace the predictor state and performance (e.g. table 
    conflicts).
\end{enumerate}

\section{LLM Disclosure}

I successfully used LLMs for rapid debugging, setting up my build system and generating the result tables. They were ineffective for programming and explaining 
branch predictor algorithms (and of course, even if they were effective, they would have harmed my learning).
